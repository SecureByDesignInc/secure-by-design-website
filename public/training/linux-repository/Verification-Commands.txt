SECURE BY DESIGN - BUILD THE LINUX REPOSITORY ON SBD-REPO01
Course 1.9 | Materials edition 1.0 | Updated 14 October 2026

Run each check in an elevated PowerShell session, or a shell on the Linux servers, on the host the lesson names.
Some lessons include the configuration commands they verify: read each command before you run it, and adapt
the example names, addresses, and paths to your own plan. Nothing in this file runs by itself.

1. Design the repository and its trust
# On SBD-ADMIN-SRV01: start the evidence folder and confirm no record exists yet
New-Item -ItemType Directory -Force C:\Evidence\linux-repository | Out-Null
Resolve-DnsName SBD-REPO01.sbd.test -Server 10.0.10.10 -ErrorAction SilentlyContinue   # expected: no answer yet
# On the approved connected system: read each upstream signing key's fingerprint
gpg --show-keys --with-fingerprint /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release    # RHEL family
gpg --show-keys --with-fingerprint /usr/share/keyrings/ubuntu-archive-keyring.gpg   # Ubuntu

What success looks like: The design names the consumers, the one distribution and the repositories mirrored; each upstream key's fingerprint matches the vendor's published value; and the register carries F19, F01, F07 and SBD-REPO01's added time row, each with an owner.

2. Build and harden SBD-REPO01
hostnamectl; ip -4 addr show
grep -E '^(pool|server|sourcedir|allow|maxdistance)' /etc/chrony.conf   # /etc/chrony/chrony.conf on Ubuntu: both controllers and maxdistance 16, nothing else
chronyc sources -v; chronyc tracking   # ^* one controller, ^+ or ^- the other; System time inside one second
sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|allowgroups) '
# On SBD-ADMIN-SRV01: export the course 1.6 root and compare its hash with course 1.6's record, then copy it over
Get-ChildItem Cert:\LocalMachine\Root | Where-Object Subject -like '*<root CA name>*' | Export-Certificate -FilePath C:\Evidence\linux-repository\sbd-root.cer
Get-FileHash -Algorithm SHA256 C:\Evidence\linux-repository\sbd-root.cer
scp C:\Evidence\linux-repository\sbd-root.cer <your-account>@SBD-REPO01.sbd.test:/tmp/
# On SBD-REPO01: the same fingerprint, then the system trust store
openssl x509 -inform der -in /tmp/sbd-root.cer -noout -fingerprint -sha256
sudo cp /tmp/sbd-root.cer /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust   # RHEL family
sudo openssl x509 -inform der -in /tmp/sbd-root.cer -out /usr/local/share/ca-certificates/sbd-root.crt && sudo update-ca-certificates   # Ubuntu
apachectl -S        # expected: one site on 10.0.70.20:80
ss -tlnp            # expected: 22 and 80, plus loopback-only listeners such as systemd-resolved
firewall-cmd --get-active-zones
firewall-cmd --list-all --zone=public   # expected: no services
curl -sI http://SBD-REPO01.sbd.test/ | head -1   # expected: 403, no directory listing

What success looks like: SBD-REPO01 resolves to 10.0.70.20 and, with course 1.3's chrony file and the hypervisor's time synchronization off, syncs from a domain controller within the course 1.3 threshold; sshd refuses root and passwords and admits only the admin group; the system trust store holds the course 1.6 root, its hash matching course 1.6's record; only TCP 22 and 80 listen; the firewall admits SSH from 10.0.60.20 alone and HTTP from the three registered consumers alone; and the web root returns 403 instead of a listing.

3. Mirror, verify, and publish a snapshot
# Connected side, RHEL family: keep vendor metadata, delete anything whose signature fails
dnf reposync --repoid=<baseos-repo-id> --repoid=<appstream-repo-id> --download-metadata --gpgcheck -p /srv/stage/2026-10-13
# Connected side, Ubuntu: Release signatures checked with gpgv against the archive keyring
debmirror --host=archive.ubuntu.com --root=ubuntu --method=http --dist=<codename>,<codename>-updates,<codename>-security --section=main --arch=amd64 --nosource --i18n --rsync-extra=none --keyring=/usr/share/keyrings/ubuntu-archive-keyring.gpg /srv/stage/2026-10-13/ubuntu
cd /srv/stage/2026-10-13 && find . -type f -print0 | sort -z | xargs -0 sha256sum > ../SHA256SUMS-2026-10-13.txt
# On SBD-REPO01, after the crossing:
cd /srv/incoming/2026-10-13 && sha256sum -c --quiet ../SHA256SUMS-2026-10-13.txt   # expected: no output
find . -name '*.rpm' -print0 | xargs -0 rpm -K | grep -v 'digests signatures OK'   # RHEL family, expected: no output
gpgv --keyring /usr/share/keyrings/ubuntu-archive-keyring.gpg ubuntu/dists/<codename>-security/InRelease   # Ubuntu
mv /srv/incoming/2026-10-13 /srv/repo/snapshots/ && restorecon -R /srv/repo/snapshots/2026-10-13   # restorecon on SELinux systems
ln -sfn snapshots/2026-10-13 /srv/repo/current.new && mv -T /srv/repo/current.new /srv/repo/current

What success looks like: The manifest check and the signature check both pass with no exceptions, /srv/repo/current points at the new dated snapshot, the previous snapshot (if any) is untouched, and the catalog entry carries the fingerprints and manifest hash.

4. Configure the Linux clients
# RHEL family
dnf repolist --all                 # expected: only the sbd-repo01 repositories enabled
rpm -q gpg-pubkey --qf '%{NAME}-%{VERSION}-%{RELEASE}\t%{SUMMARY}\n'
dnf makecache && dnf info rsyslog-gnutls | grep -Ei '^(repository|from repo)'
# Ubuntu
apt-get update                     # expected: no errors or warnings
apt-cache policy | grep -E 'http'   # expected: only SBD-REPO01.sbd.test
apt-cache policy rsyslog-gnutls
# Both: hash the client package for the later courses
sha256sum /srv/repo-records/client/*

What success looks like: On SBD-REPO01 the package manager lists SBD-REPO01 as its only source, trusts only the verified keys, refreshes without errors, and resolves rsyslog-gnutls from the snapshot; the client package is hashed and filed.

5. Keep it current and prove it
# On SBD-REPO01: promote the next snapshot, then rehearse rollback
readlink /srv/repo/current
ln -sfn snapshots/2026-11-10 /srv/repo/current.new && mv -T /srv/repo/current.new /srv/repo/current
ln -sfn snapshots/2026-10-13 /srv/repo/current.new && mv -T /srv/repo/current.new /srv/repo/current   # rollback
# On SBD-ADMIN-SRV01: no output means every staged file is on the connected-side list
(Get-ChildItem C:\Staging\DISA\linux\* -File -Exclude *.csv | Get-FileHash -Algorithm SHA256).Hash | Where-Object { $_ -notin (Import-Csv C:\Staging\DISA\linux\connected-side-hashes.csv).Hash }
scp C:\Staging\DISA\linux\<SCC for Linux package> C:\Staging\DISA\linux\<STIG benchmark> <your-account>@SBD-REPO01.sbd.test:/tmp/
# On SBD-REPO01: the same hashes, then SCC's command-line scanner as root (path and options from the SCC readme)
sha256sum /tmp/<SCC for Linux package> /tmp/<STIG benchmark>
sudo <SCC install directory>/cscc
# On SBD-ADMIN-SRV01: collect the session and the record, then hash everything
New-Item -ItemType Directory -Force C:\Evidence\linux-repository\baseline | Out-Null
scp -r <your-account>@SBD-REPO01.sbd.test:<SCC session folder> C:\Evidence\linux-repository\baseline\SBD-REPO01
scp -r <your-account>@SBD-REPO01.sbd.test:/srv/repo-records/* C:\Evidence\linux-repository\
Get-ChildItem C:\Evidence\linux-repository -Recurse -File | Get-FileHash -Algorithm SHA256 | Export-Csv C:\Evidence\linux-repository-hashes.csv -NoTypeInformation

What success looks like: The cadence is written with an approver, the promotion and the rollback both show in the catalog and in the client's view, the Linux assessment set sits checked in C:\Staging\DISA\linux on SBD-ADMIN-SRV01, SBD-REPO01 has a first baseline with every open item classified, and the record and handoff are filed with hashes.
