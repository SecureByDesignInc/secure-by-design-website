Prove you can recover

Close the Build path by proving the network can come back: scheduled directory and CA backups under ceremony-grade custody, policy, boundary, logs, and the living records in one hashed catalog, a timed restore rehearsal in isolation, and the recovery record that completes the Body of Evidence.

Before you start · prerequisites and lab plan
  • Complete courses 1.1–1.9: the full network, its records, and the protected log archive all exist.
  • Provision a protected backup volume on each server, written only by its backup job, an offline backup cabinet with removable media and a custody register, and an isolated recovery network segment (or host) for the restore rehearsal.
  • Have the custody records handy: the Directory Services Restore Mode (DSRM) passwords from course 1.1 and the CA key protection decisions from course 1.4 — recovery is where those promises come due.

The model's final chapter: a network that cannot come back was never really built. This course backs up what matters — directory, certificate authority, policy, boundary, and the log record — proves one real restore in isolation, and files the tested-recovery evidence the authorization path expects.

YOUR LEARNING PATH

LESSON 1 OF 6 · ABOUT 20 MIN

Decide what recovery must prove

Recovery starts as a list of promises: which systems and records must be restorable, how old a restored copy may be, how long restoration may take — written as commitments the rest of the course exists to keep.

In this lesson you will

  • Name the recovery set: what must come back, in what order.
  • Set the recovery point and time objectives per item.
  • Decide where backups live and who can touch them.

Work through the configuration

  1. Write the recovery set in dependency order — the same order the path built it: the directory first (everything trusts it), then the CA's database and keys, Group Policy, the router configuration, the log archive, and the living records themselves (register, inventory, exception record).
  2. Set the two numbers per item: how much history may be lost (recovery point) and how long restoration may take (recovery time) — lab-honest values you will actually measure against in lesson 5, not aspirations.
  3. Decide backup placement: each server's protected backup volume is written only by the backup process and readable by the recovery role, and a custodian carries copies to the offline backup cabinet on media — the air-gapped network's version of an off-site copy. There is no network path to the cabinet.
  4. Confirm the standing custody items: the DSRM passwords are sealed and findable, and the root CA's protected backup from the course 1.4 ceremony is accounted for — recovery depends on secrets that must exist before the bad day.

Inspect your configuration

Run the relevant checks in an elevated PowerShell session — or a shell, on the Linux servers — on the host identified in the lesson. Adapt the example names and paths to your lab.

# Capture the current protection state before this course changes it.
wbadmin get versions
Get-ChildItem E:\Backups -ErrorAction SilentlyContinue | Measure-Object   # this server's protected backup volume

What success looks like

The recovery set is ordered by dependency with point and time objectives per item, the backup placement and access rules are written, and the DSRM and root-key custody records check out.

Keep your evidence

Keep the recovery requirements sheet, the objectives table, the placement and access decisions, and the custody verification notes.
