Design the two-tier trust hierarchyAbout 25 min · Open this lessonDraw the hierarchy: offline standalone root → enterprise issuing CA → approved server/client certificates.
There is no network connection to the root.Record final host and CA names, key provider, algorithm, key sizes, hashes, validity periods, renewal owners, and recovery arrangements.
Start from this lab's example values in the next step and change any that your own policy requires: they are examples, not universal requirements.Example values for this lab: the root CA uses an RSA 4096 key with SHA-256 and a 20-year certificate, and publishes a base CRL every 26 weeks with an overlap period and no delta CRL, refreshed at each offline ceremony.
The issuing CA uses RSA 4096 (3072 at minimum) with SHA-256 and a 10-year certificate, a weekly base CRL, and a daily delta CRL.
End-entity certificates last one to two years.
NIST SP 800-57 Part 1 rates RSA 2048 at 112 bits of security, which it accepts for new signatures only through 2030, so a CA that will still be signing after 2030 uses at least 3072 bits (128 bits of security); Windows Server 2025 requires at least 2,048-bit RSA for TLS server authentication.Know where each value is set.
You choose the key, the hash, and the root's 20-year validity in the AD CS Configuration wizard.
Each CA's CAPolicy.inf sets its CRL periods (CRLPeriod, CRLPeriodUnits, CRLDeltaPeriod, CRLDeltaPeriodUnits), which certutil -setreg can change later.
The issuing CA's 10-year lifetime is set on the root (CA\ValidityPeriod and CA\ValidityPeriodUnits) before the signing ceremony, because a subordinate CA's lifetime comes from the CA that signs it.Plan a stable internal publication name such as pki.sbd.test.
The Authority Information Access (AIA) location supplies issuer certificates; the CRL Distribution Point (CDP) supplies certificate revocation lists.Choose the publication host, paths, access rules, and refresh schedule before issuing certificates.
Clients inside this air-gapped network must reach those locations without relying on the public internet.Commands:# Run on the future issuing CA, not the offline root.
Get-CimInstance Win32_ComputerSystem | Select-Object Name, Domain, PartOfDomain Resolve-DnsName SBD-DC01.sbd.test Resolve-DnsName SBD-DC02.sbd.testVerify: The written plan separates trust, issuance, publication, and administration.
It identifies who renews CRLs before they expire, and every key size, hash, lifetime, and CRL period has a recorded value and the setting that applies it.Evidence: Keep the approved hierarchy, the cryptography and lifetime table with the setting that applies each value, and a worksheet mapping every certificate/CRL URL to its actual publisher and file.Notes / result / date:2.
Configure the offline Root CAAbout 30 min · Open this lessonVerify SBD-ROOTCA01 is in a workgroup with no active network path.
Prepare approved installation media, protected administration, correct time, and backup storage.Place the reviewed CAPolicy.inf in %SystemRoot% before configuration.
Tailor it to the root role: in this lab it sets CRLPeriod=Weeks and CRLPeriodUnits=26, and CRLDeltaPeriodUnits=0 so the root publishes no delta CRL.
A self-signed root's own CDP/AIA choices differ from the extensions the root places into issued subordinate certificates.Install the Certification Authority role with management tools.
In the AD CS Configuration wizard choose Standalone CA, Root CA, and a new private key, then apply the approved provider, cryptography (RSA 4096 with SHA-256 in this lab), CA name, validity (20 years), database, and log settings.Before signing anything, configure the root's issued-certificate AIA/CDP settings, the subordinate validity policy (CA\ValidityPeriod Years and CA\ValidityPeriodUnits 10 in this lab), and the base-CRL schedule (26 weeks with an overlap period, and no delta CRL).
Hold requests for explicit approval.
Produce and inspect a current root CRL, then capture a protected CA backup.Commands:# Inspect locally on SBD-ROOTCA01 during the approved root session.
Get-CimInstance Win32_ComputerSystem | Select-Object Name, Domain, PartOfDomain Get-Service CertSvc certutil -getreg CA\CRLPublicationURLs certutil -getreg CA\CACertPublicationURLs certutil -getreg CA\ValidityPeriodUnits certutil -getreg CA\CRLPeriodUnitsVerify: The host remains disconnected, the CA is standalone/root, requests require approval, and the planned subordinate URLs and 10-year subordinate validity are configured before signing.Evidence: Record the root certificate identity, policy file, publication settings, CRL dates, backup location, and operator sign-off.
Protect backups containing private keys.Notes / result / date:3.
Create the issuing CA requestAbout 25 min · Open this lessonConfirm SBD-SUBCA01 has its final hostname, domain membership, static address, internal DNS, and correct time.
Use a dedicated host and the privileges approved for enterprise CA configuration.Prepare its role-specific CAPolicy.inf (in this lab: CRLPeriod=Weeks, CRLPeriodUnits=1, CRLDeltaPeriod=Days, CRLDeltaPeriodUnits=1, and LoadDefaultTemplates=0) and protected request directory.
Decide which templates may later be published instead of enabling a broad default enrollment set.Install the CA role and management tools.
In the AD CS Configuration wizard choose Enterprise CA, Subordinate CA, and the approved new-key/provider settings (RSA 4096 with SHA-256 in this lab).
Enter the planned CA identity and storage locations.Choose Save a certificate request to file.
Inspect the resulting request's subject, public key, and CA constraints; record its SHA-256 hash before handing it to the media custodian.Commands:# Use the actual request path chosen in the wizard.
certutil -dump C:\CAConfig\IssuingCA.req Get-FileHash -Algorithm SHA256 C:\CAConfig\IssuingCA.reqVerify: The request matches the approved issuing identity and key profile.
The CA is waiting for its signed certificate; do not troubleshoot that expected state by installing another CA.Evidence: Retain the request, its reviewed fields and hash, and the request-transfer record.
Do not place private keys in the transfer package.Notes / result / date:4.
Sign through the offline ceremonyAbout 30 min · Open this lessonUse approved removable media and custody procedures to bring the request to the root.
Recalculate its hash and compare it with the independently recorded value; inspect the request before submission.Verify the root's issued-certificate validity policy and publication extensions.
In Certification Authority, submit the request, review its pending entry, and issue it only after the required approval.Export the subordinate certificate, root certificate, and current root CRL.
Check identities, constraints, validity, signatures, URLs, and revocation data against the approved hierarchy.
Record file hashes and the request ID.Transfer only the approved public artifacts back to the connected environment.
Match published filenames to the URLs embedded in certificates, retain the ceremony record and protected backup, then shut down and secure the root.Commands:# Inspect public artifacts; use your actual approved paths.
certutil -dump C:\CAConfig\IssuingCA.cer certutil -dump C:\CAConfig\RootCA.crl Get-FileHash -Algorithm SHA256 C:\CAConfig\IssuingCA.cer, C:\CAConfig\RootCA.cer, C:\CAConfig\RootCA.crlVerify: Artifact identities, signatures, validity, and custody checks pass.
The root remains offline; a field dump alone is not end-to-end trust validation.Evidence: Keep approval, request ID, artifact hashes, verified certificate/CRL properties, media custody, and root shutdown evidence together.Notes / result / date:5.
Activate issuance and publish trust dataAbout 30 min · Open this lessonVerify the returned artifacts and import the approved root certificate into the issuing server's trusted root store.
Complete CA certificate installation through Certification Authority and start Certificate Services.Configure the issuing CA's AIA/CDP settings before issuing test certificates.
Publish current root and issuing certificates and CRLs to the planned internal locations, preserving the actual filenames referenced by their extensions.Distribute the approved root trust through the managed domain policy and arrange the required intermediate/directory publication with delegated administrators.
Public CA certificates and CRLs may be readable to clients; private keys and backups must never enter that web directory.Publish only the certificate templates required for the lab.
Review purpose, subject construction, key settings, validity, and enrollment permissions; grant a small test group the minimum enrollment rights first.Commands:# Inspect the issuing CA after installation and publication.
Get-Service CertSvc certutil -getreg CA\CRLPublicationURLs certutil -getreg CA\CACertPublicationURLs certutil -store Root certutil -store CAVerify: Issuance is configured, the approved trust chain reaches the client, and the exact published URLs return the current files from the internal network.Evidence: Keep publication mappings, permissions, template settings, trust-distribution policy, and retrieval results.Notes / result / date:6.
Validate enrollment, revocation, and recoveryAbout 25 min · Open this lessonEnroll a disposable test certificate using the approved template.
Export only its public certificate as test.cer and inspect the subject, purpose, issuer, and validity.On a clean validation client, verify the chain and retrieval using the command below.
Inspect each AIA/CDP URL and current CRL dates; cached success is insufficient evidence of publication reachability.Revoke only the disposable test certificate, publish an updated issuing CRL, and verify that a fresh client evaluation detects revocation.
Diagnose retrieval or stale-publication problems rather than turning off revocation checks.Record owners and reminders for root/issuing CRL publication, certificate renewal, backup, and an isolated recovery rehearsal.
Schedule offline root ceremonies early enough to transfer and publish replacement CRLs before expiry.Commands:# On the validation client; test.cer is the disposable public certificate.
certutil -dump test.cer certutil -urlfetch -verify test.cerVerify: A valid test certificate chains to the approved root and retrieves current revocation data.
After revocation and publication, the test certificate is rejected for the expected reason.Evidence: Finish the PKI checklist with enrollment, retrieval and revocation results, renewal dates, backup verification, and recovery ownership.Notes / result / date:SourcesMicrosoft · PKI design considerationsMicrosoft · CAPolicy.inf syntaxMicrosoft · Install the offline rootMicrosoft · Deploy the issuing CA roleMicrosoft · Perform the offline root signing ceremonyMicrosoft · Publish trust data and validate clientsMicrosoft · Certutil referenceNIST · SP 800-57 Part 1 Rev.
